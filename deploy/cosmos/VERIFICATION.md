## Two defects found by this run, and fixed

1. **Healthcheck units** — Cosmos decodes healthcheck `interval`, `timeout` and
   `start_period` as integer seconds. The template initially used `"15s"` strings,
   which would make the install fail during container creation. Fixed to integers.
2. **Route array order** — Cosmos prepends each service route to the stored route
   list. The template initially listed UI, health, API, which produced the reverse
   order in Cosmos and let the UI catch-all win. The template now lists API,
   health, UI so the stored order is UI, health, API.

Both fixes are in `deploy/cosmos/MediaManager/cosmos-compose.json` on main
(PR #74) and in the official store PR #336.

## 2026-10-30 template correction

The canonical market template keeps the Cosmos-wizard-compatible lowercase
Compose keys (`type`, `source`, `target`, `readOnly`) and adds
`bindOptions.propagation: rslave` plus `readOnly: true` for the AltMount parent.
The uppercase Docker API spelling crashes the supported Cosmos market wizard,
which calls `volume.source.startsWith(...)`; Docker's API decoder accepts the
lowercase keys case-insensitively. The template therefore fixes wizard
compatibility without dropping propagation.

This static review did **not** install the changed template against a live
Cosmos instance. The previous verification submitted a rendered payload directly
to the service API, which bypasses the wizard. Before claiming a safe market
install, perform a disposable wizard install and verify:

1. AltMount is configured with `fuse.read_only: true` and its host parent is a
   shared mount; the API's `/mnt` bind is read-only with `rslave`.
2. `findmnt` shows the FUSE mount read-only, and a write from the API container
   fails before and after replacing the FUSE child mount without recreating the
   API container.
3. `/api` and `/health` route to the API, the UI route does not capture `/api`,
   and the injected bearer token works without exposing it in the browser.
4. The PostgreSQL data volume survives API/UI container recreation, and a fresh
   install reaches healthy only after migrations complete.

Until that disposable run is recorded, the FUSE-remount and wizard assumptions
remain untested.

## 2026-10-30 route host and owner-auth correction

The API, health and UI routes now all declare `useHost: true`, the same explicit
`host`, `AuthEnabled: true` and `AdminOnly: true`. Cosmos 0.23.4 only adds a
host matcher when `UseHost` is true (`src/proxy/routerGen.go`); with the previous
`useHost: false`, `/api` and `/health` could match on another Cosmos app host.
`AdminOnly: true` uses Cosmos's admin permission gate (`PERM_ADMIN_READ`), so a
signed-in non-admin Cosmos user cannot receive the injected Media Manager owner
token.

Manual disposable validation still required:

1. On the intended Media Manager host, `/api/v1/dashboard` with a valid owner
   session returns 200 and `/health/ready` is reachable; the UI catch-all does
   not capture either path.
2. On a different Cosmos app host, the same `/api` and `/health` paths do not
   proxy to Media Manager.
3. A signed-in non-admin Cosmos user is refused by all three routes; the owner
   (Cosmos admin) succeeds.
4. A reverse proxy in front of Cosmos preserves the configured Host header; an
   IP-only or alternate-host request is not expected to match.

These checks have **not** been run against the live Cosmos instance. This PR
changes only the install template; existing Cosmos installs need their three
routes corrected manually and rechecked. Cosmos may show separate hostname
fields for the API and health routes, but because all three routes use the same
`{Hostnames...}` placeholder, the intended value is the Media Manager host
shown for the UI route; verify the stored routes after installation.
